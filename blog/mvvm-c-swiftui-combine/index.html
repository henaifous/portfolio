MVVM-C with SwiftUI and Combine: navigation that stays testable

SwiftUI makes it easy to push navigation into the view layer, and that is exactly what makes screens hard to test and reuse. MVVM-C adds one more role, the coordinator, so views render, view models decide and one object owns where the app goes next.

What the C adds

MVVM splits a screen into three parts. The view draws state and forwards taps. The view model holds that state and the logic behind it. The model or service layer fetches and stores data. It works well until a tap has to open another screen.

The usual shortcut is a NavigationLink inside the view, or a view model that knows about the next screen. Both tie screens together: a list now knows how to build its detail view, and a unit test for the list has to cope with navigation it does not care about.

MVVM-C, which is MVVM with Coordinators, removes that coupling with one rule: nobody except the coordinator knows what comes next.

  • View: renders state and sends intents such as taps. It never creates another screen.
  • View model: owns state and logic. It reports what happened as events, without saying where to go.
  • Coordinator: listens to events, owns the navigation path and builds each screen with its dependencies.
Note

The examples target iOS 16 and later, where NavigationStack takes a path you can own. The same roles work with UIKit and older SwiftUI.

Routes and the coordinator

Start by naming every destination as a value. A Hashable enum works with NavigationStack, survives state restoration and doubles as a deep-link format.

The coordinator is an ObservableObject because NavigationStack reads and writes its path through a binding. Anything that changes path, whether a tap, a deep link or a test, changes what is on screen.

View models emit events

The list view model needs no idea that a detail screen exists. It publishes what happened and nothing else.

@Published carries state to the view. A PassthroughSubject carries one-off events to the coordinator. Events are not state: a navigation request should fire once and be forgotten, not sit in a property that the next screen reads again.

Wiring the two with Combine

The coordinator creates the view model, subscribes to its events and translates each one into a route.

Detail screens are built when the route is shown. The coordinator hands each one its dependencies, and the view creates its view model through StateObject.

SwiftUI can call destination(for:) many times. Passing the view model through an autoclosure into StateObject means it is built once for the life of the screen, not on every refresh.

Testing without a UI

Both halves test with plain XCTest and no view hierarchy. The view model test checks the event. The coordinator test checks the route.

Deep links get the same treatment: parse a URL into [Route], assign it to path and assert on the result.

Mistakes to avoid

  1. Building view models in body. A view model created inside body is recreated on every refresh and loses its state. Create it once, in the coordinator or inside the StateObject autoclosure.
  2. Strong references in sink closures. The coordinator owns the subscription, and the closure points back at the coordinator. Capture [weak self].
  3. One giant route enum. When a flow such as sign-up or checkout has its own steps, give it a child coordinator with its own path and let it report back when it finishes.
  4. Treating events as state. If a screen only works when a @Published flag flips, you have rebuilt the problem MVVM-C removes. Use a subject for one-off events.
Threading

A PassthroughSubject delivers on the thread that calls send, and path drives the UI. Keep these types on the main actor, or add .receive(on: DispatchQueue.main) before the sink.

In short

Give each role one job: views render, view models decide, the coordinator navigates. You get screens that preview and test in isolation, navigation you can drive from a deep link, and flows you can rearrange without touching a single view.
