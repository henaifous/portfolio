From iOS to Flutter: what carries over and what does not

If you have shipped iOS apps, Flutter feels familiar within a day and surprising within a week. This guide maps SwiftUI concepts to their Flutter counterparts, then lists the habits that need to change.

Same ideas, different names

I work on iOS and Flutter code side by side, and most of what you know transfers. Both frameworks describe the interface as a function of state, both rebuild cheaply, and both reward small, testable pieces. What changes is the vocabulary.

Provider and Riverpod are packages, not part of Flutter itself. Pick one state approach per app and stay with it.

Layout: modifiers become wrappers

SwiftUI chains modifiers onto a view. Flutter wraps a widget in another widget. Here is the same two-line label in both.

Two consequences follow. Padding, alignment and sizing are widgets, so trees get deeper and you extract small widgets earlier than you would extract views. And const constructors, as in const SizedBox(height: 8), let Flutter skip rebuilding parts that cannot change.

State and rebuilds

@State and setState both say the same thing: this screen owns a value and should redraw when it changes. The difference is that Flutter makes the notification explicit.

For state shared between screens, the closest match to ObservableObject is ChangeNotifier. Compare the two models.

@Published fires on every assignment. A ChangeNotifier only tells its listeners when you call notifyListeners(). Forget it and the screen quietly stays stale, which is the most common first bug for iOS developers.

Navigation

Flutter's Navigator keeps a stack of routes, much like NavigationStack. Pushing a screen is one call.

For deep links, URLs and the web, most teams adopt a router package such as go_router, which describes every route in one place. If you came from a coordinator-based iOS app, that configuration plays the same role: it is the one place that knows how screens connect. I wrote about that pattern in MVVM-C with SwiftUI and Combine.

Async code and streams

async/await reads almost the same in both languages. Combine publishers map to streams, and a cancellable maps to a subscription that you must cancel yourself.

Combine's AnyCancellable cancels itself when it is released. A StreamSubscription does not, so cancel it in dispose().

Testing

XCTest becomes flutter_test. A widget test builds a widget in memory and lets you tap it and read the result, with no simulator.

That runs in milliseconds on your machine, so it is cheap to cover screens that would need a slow UI test on iOS.

Habits that break

  • Value types. Dart has no structs. Immutable models are classes with final fields, usually with a copyWith method or a code generator.
  • build() runs often. Treat it like SwiftUI's body: no network calls and no side effects. Keep it cheap and push work into state.
  • No live previews to lean on. Hot reload keeps your app's state while you edit, which covers much of what previews are used for.
  • Platform look. Material widgets are the default. For an iOS look, use the Cupertino widgets deliberately, screen by screen.
  • Optionals. Dart's null safety is close to Swift optionals, with String?, ?? and !. Avoid force unwrapping in Dart the way you avoid it in Swift.

In short

Most of your SwiftUI instincts carry over: declare the interface from state, keep logic out of views and test small units. What changes is the vocabulary, the explicit rebuild signals and the lack of value types. Map the concepts first, then learn the packages.
